# heyee-agent：MCP Client 与对话编排实施清单

## 1. 目标与边界

`heyee-agent` 是用户对话、知识库检索和 MCP 工具调用的编排端。订单、售后、物流、优惠券等数据属于另一个业务项目；该项目作为 MCP Server 暴露业务工具。

本项目的责任是：**发现远程工具、识别何时调用、抽取受控参数、调用工具、格式化结果，并把结果安全地提供给 LLM。**

本项目不负责业务工具的具体注册实现，不直连对方数据库或 Redis，不复制订单状态机、权限规则或缓存 Key。远程工具的实现、数据正确性、权限和审计仍由业务项目负责。

## 2. “注册工具”的职责说明

为避免两边重复实现，必须区分两类注册：

1. **业务项目的 Server 端注册**：把 `order_query` 等工具定义和处理器注册到 MCP Server，并通过 `tools/list` 暴露。
2. **本项目的 Client 端发现/登记**：连接 MCP Server 后调用 `tools/list`，为发现到的远程工具创建调用代理并登记到本地运行时 Registry。

本项目只做第二类。不要在代码中为每个订单/物流工具写固定执行器或复制其 JSON Schema；应根据 Server 返回的工具定义自动发现。意图节点中的 `mcp_tool_id` 只引用远程工具名。

## 3. 对接上下文与目标流程

用户问题可能同时包含知识库问题和实时业务问题，例如“退货政策是什么，我的订单退款到哪一步了？”。知识库路径与 MCP 路径可并行，但结果必须分开保留并在生成阶段汇合。

```text
Chat Pipeline
  -> 加载会话记忆 / 改写查询 / 拆分子问题
  -> 意图识别：KB、MCP、SYSTEM
  -> KB 检索 与 MCP 工具调用并行
       -> MCP：按 mcp_tool_id 取远程工具代理
       -> 按工具 Schema 抽取、校验参数
       -> tools/call 调用业务 MCP Server
  -> 分别格式化 kbContext 与 mcpContext
  -> 将受控上下文交给 LLM，生成最终回答
```

## 4. 需要完成的事项

### 4.1 MCP Client 配置与连接管理

- [ ] 增加 MCP Server 配置：服务名、URL、传输方式、认证信息引用、连接/读取超时、启用开关、环境标签。
- [ ] 凭证从密钥管理或环境变量读取，严禁写入意图节点、数据库明文配置或日志。
- [ ] 在应用启动或受控的后台刷新任务中，完成 MCP `initialize` 握手和 `tools/list` 发现。
- [ ] 为每个发现到的远程工具创建 Client 端调用代理，并放入本地运行时工具 Registry，键为远程工具名。
- [ ] 多个 Server 中出现同名工具时必须启动失败或显式命名空间化；不得静默覆盖。
- [ ] 单个 MCP Server 不可用时，记录健康状态并跳过该 Server；不能因此阻止 Agent 服务启动。
- [ ] 关闭服务时释放 MCP 连接、HTTP 客户端和后台刷新任务。

### 4.2 意图树与工具映射

- [ ] 将实时数据查询意图配置为 `kind=MCP`，并填写 `mcp_tool_id`。
- [ ] `mcp_tool_id` 必须严格等于业务项目通过 `tools/list` 返回的工具名；启动校验或定期校验不匹配项。
- [ ] 在意图节点维护用户可理解的描述、示例问法、参数抽取提示和回答规则片段；不在这里保存业务连接信息或实现逻辑。
- [ ] 将 `KB`、`MCP`、`SYSTEM` 意图分流：KB 用于文档检索，MCP 用于实时工具调用，SYSTEM 用于无需检索的固定流程。
- [ ] 对多子问题和多意图设置总量上限及每个子问题的上限，防止一次输入触发大量远程调用。

示例意图节点：

```text
id = commerce-order-progress
kind = MCP
mcp_tool_id = order_query
description = 查询用户订单、退货或退款的实时状态
examples = 我的退款到哪一步了？/ 订单 2024112801 什么时候退款？
param_prompt_template = 提取订单号和查询类型；缺少订单标识时标记为需要澄清
prompt_snippet = 回答订单问题时只依据工具返回的实时数据，不要臆测处理时间
```

### 4.3 参数抽取、校验与澄清

- [ ] 使用远程 `tools/list` 返回的 JSON Schema 作为参数抽取和校验的唯一依据。
- [ ] 从用户问题中抽取参数后，在本地做类型、枚举、格式和必填字段校验；不能让不合法参数进入业务 Server。
- [ ] 用户身份、租户、渠道等安全上下文按双方约定从受信任会话/令牌传递，不能由模型或用户文本决定。
- [ ] 缺少订单号等关键定位条件时，优先返回澄清问题，例如“请提供订单号，或说明需要查询的订单”；不得泛查用户全部订单后交给模型筛选。
- [ ] 对模型生成的参数限制长度、数组数量、时间范围和查询条件组合，防止提示注入或资源放大。
- [ ] 日志只记录脱敏参数摘要，完整工具参数不得进入普通应用日志。

#### 4.3.1 参数提取的处理流程

参数提取发生在 Client 端：输入为“用户原始问题 + 已发现工具的 JSON Schema”，输出为准备传给 `tools/call` 的参数对象。它不是业务查询，也不应把自然语言或模型回答直接拼接到请求中。

```text
远程 Tool Schema + 用户原始问题
  -> 将 Schema 转成模型可读的工具定义文本
  -> 构建受控的 System Prompt + User Prompt
  -> 低随机性、非流式调用 LLM，要求只返回 JSON 对象
  -> 清理 Markdown 围栏并解析 JSON
  -> 仅保留 Schema 白名单字段，做类型转换
  -> 对缺失字段填充 Schema 默认值
  -> 本地校验；缺少关键必填项则澄清，合法时 tools/call
```

- [ ] Schema 文本至少包含工具 ID、功能描述、参数名、类型、必填/可选、描述、默认值、枚举和格式限制；不要让 LLM 依据代码字段名猜测语义。
- [ ] 参数抽取优先使用工具 Schema 中的 `description`、`enum` 和 `default`，而不是为每个工具维护正则规则。自然语言中的口语表达、相对时间、中文数字等由 LLM 归一到契约值。
- [ ] 使用低随机性参数提取（建议 `temperature=0.1`、`top_p=0.3`），关闭不必要的推理输出，并使用非流式调用，以获得完整 JSON 后再解析。
- [ ] 工具/意图确有特殊格式需要时，可在意图节点配置 `param_prompt_template` 覆盖默认 System Prompt；覆盖模板也必须保留安全规则和 JSON 输出约束。

#### 4.3.2 Prompt 边界与提示注入防护

System Prompt 必须明确以下约束：工具定义和提取规则优先于用户问题；用户问题只是**参数来源文本**，不是指令。模型只能输出 Schema 中已有的字段，不能杜撰字段、不能将用户文本中的指令当作系统指令，也不能为了凑齐参数而编造事实。

- [ ] 用四种参数情况定义确定行为：必填且无默认值（缺失则标记澄清）、必填且有默认值（按 Schema 默认值补齐）、可选且有默认值（未提及则补齐）、可选且无默认值（未提及则省略）。
- [ ] 只允许输出严格 JSON 对象，不允许附加解释、Markdown、注释或工具调用指令。
- [ ] 用户明确提供的值优先于默认值；默认值只填充缺失字段，绝不能覆盖已提取值。
- [ ] 枚举值只可映射到 Schema 已声明的规范值；无法可靠映射时不应猜测，应触发澄清或交由服务端返回参数错误。

#### 4.3.3 响应解析、白名单与类型处理

LLM 的输出不可信，必须在调用远程工具前进行防御性处理：

- [ ] 清理可能的 Markdown 代码围栏后解析 JSON；返回空文本、非对象、数组、非法 JSON 或含有额外说明时，均视为提取失败，而不是抛出未处理异常。
- [ ] 以 Schema 的 `properties` 作为字段白名单，只保留已声明且非 `null` 的键；丢弃例如 `format`、`explain` 等模型杜撰字段。
- [ ] 按 Schema 做类型转换和校验。尤其要正确处理 JSON 数值没有 `int`/`float` 区分的问题：仅当数值无小数部分且在范围内时，才可转换为整数；布尔值、数组和对象也要按 Schema 验证。
- [ ] 客户端校验是减少无效远程调用的第一道防线；业务项目仍必须做权威的服务端校验，Client 不替代 Server 的权限或业务参数校验。
- [ ] 使用可变参数对象完成默认值填充，避免因不可变 Map 导致运行时失败。

#### 4.3.4 默认值与降级策略

- [ ] `fillDefaults` 只遍历当前 Tool Schema：当参数缺失且该字段声明了 `default` 时补充；未声明默认值的可选参数保持省略。
- [ ] LLM 调用超时、网络异常、JSON 解析失败或输出不符合对象约束时，不能将原始用户问题作为参数转发。
- [ ] 降级结果只能使用该 Schema 内、已声明的默认值；若默认值不足以满足必填字段，应转为澄清问题，而非发起宽泛的业务查询。
- [ ] 分别记录“提取成功”“解析失败”“默认值降级”“需要澄清”和“服务端拒绝”等指标，便于发现 Schema 描述或 Prompt 的质量问题。

### 4.4 工具调用与并发控制

- [ ] 根据 `mcp_tool_id` 从本地 Registry 找到远程工具代理，调用 MCP `tools/call`。
- [ ] 使用专用、有限大小的 MCP 调用并发池/队列；不要与 KB 检索或 Web 请求无限制抢占资源。
- [ ] 为单调用和整轮对话设置超时预算；总预算应覆盖参数抽取、网络调用、格式化和 LLM 生成。
- [ ] 只对幂等查询执行有限重试，并遵循业务项目给出的限流与重试建议。
- [ ] 统一处理网络错误、工具返回 `isError`、超时和工具不存在；单个工具失败不得中断 KB 检索或整轮对话。
- [ ] 保留调用 traceId，并向业务项目透传关联 ID，便于跨项目定位问题。

### 4.5 结果格式化与 LLM 上下文保护

- [ ] 将 MCP 结果和 KB 结果分别保存为 `mcpContext`、`kbContext`，在最后的 Prompt 构建阶段再汇合。
- [ ] 保留工具名、成功/失败状态和经过清洗的结构化数据；不要把原始 SDK 对象或异常堆栈直接交给模型。
- [ ] 对结果设置条数、字段白名单和文本长度限制；优先使用业务项目返回的安全摘要及经过确认的字段。
- [ ] 工具错误应以可解释但不泄密的上下文提供给 LLM，例如“实时物流服务暂不可用”，避免模型编造结果。
- [ ] 当 MCP 上下文存在时，使用更低随机性生成回答，并在 Prompt 中明确“实时状态仅以工具结果为准”。
- [ ] 用户问题包含多个子问题时，对每个结果保留问题索引和工具来源，避免模型将某个订单结果回答到另一个子问题上。

### 4.6 可用性、监控与运维

- [ ] 为每个 MCP Server 维护连接状态、最后成功发现时间、工具数量、最近失败原因和熔断状态。
- [ ] 记录工具名、Server 名、调用结果、耗时、重试次数和错误类别；对用户问题及业务数据做脱敏。
- [ ] 监控成功率、P95/P99 延迟、超时率、工具发现失败率、Schema 不匹配数、限流数和调用量。
- [ ] 设定故障降级文案与前端/接口响应策略：工具不可用时说明无法获得实时数据，不以知识库旧文档冒充实时查询结果。
- [ ] 工具目录变化时支持受控刷新；刷新失败时继续使用最近一次已验证的目录，或按策略暂时下线该 Server。

## 5. 与业务项目共同确认的契约

联调前双方必须确认以下内容：

| 项目 | 约定内容 |
| --- | --- |
| Server 接入 | 环境地址、MCP 传输方式、网络策略、认证方式、证书/Token 轮换 |
| 工具目录 | 工具唯一 ID、描述、输入 Schema、默认值、枚举、最大响应大小 |
| 身份上下文 | 用户、租户、渠道、角色和 traceId 的可信传递方式 |
| 结果语义 | 正常、无数据、参数错误、无权限、限流、超时、系统异常的统一识别方式 |
| 性能预算 | 单工具超时、总对话预算、并发配额、重试和熔断策略 |
| 数据安全 | 可返回字段、需脱敏字段、禁止进入 Prompt/日志的字段 |
| 变更管理 | Schema 兼容规则、发布窗口、灰度方式、回滚与负责人 |

## 6. 验收标准

- [ ] 配置一个 MCP Server 后，本项目可完成握手、`tools/list` 发现和远程工具代理登记。
- [ ] 不需要为每个业务工具增加本地硬编码实现；新工具可通过 Server 发布 + 意图配置接入。
- [ ] `MCP` 意图能够准确引用已发现的工具；不存在或 Schema 不匹配时有明确告警和安全降级。
- [ ] 缺少关键参数时会澄清，不会发起宽泛查询或让模型猜测业务结果。
- [ ] 工具成功、无数据、无权限、超时、限流、网络异常均能得到正确的用户可理解结果，且不泄露内部信息。
- [ ] MCP 工具故障不会阻断 KB 路径、其他工具或 Agent 服务启动。
- [ ] 已具备端到端 trace、工具级监控、脱敏日志和关键异常告警。
