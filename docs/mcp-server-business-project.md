# 业务项目：MCP Server 实施清单

## 1. 目标与边界

本项目是订单、售后、物流、优惠券等实时业务数据的**唯一数据拥有方**。需要将可供智能问答使用的业务查询能力，以 MCP（Model Context Protocol）工具的形式对外提供给 `heyee-agent`。

`heyee-agent` 不应直接连接本项目的数据库或 Redis，也不应依赖 DAO、Repository、Mapper、缓存 Key 等内部实现。本项目需要复用已有的应用服务或查询服务，在 MCP 工具中完成业务校验、权限控制和数据查询。

本项目的责任是：**注册并暴露工具、执行真实业务查询、保证数据与权限正确性。** 不负责知识库检索、意图识别、参数的自然语言抽取和 LLM 最终回答。

## 2. 对接上下文

用户可能提出以下问题：

- “我上周提交的退货申请到哪一步了？”
- “订单 2024112801 的物流到哪里了？”
- “我的优惠券余额还有多少？”

这类问题需要查询实时业务数据，不能只依赖知识库。调用链为：

```text
用户问题
  -> heyee-agent：识别 MCP 意图、抽取工具参数
  -> 本项目 MCP Server：接收 tools/call
  -> 本项目已有应用服务：查询 DB / Redis / 下游服务
  -> 本项目 MCP Server：返回结构化工具结果
  -> heyee-agent：将结果作为上下文，生成最终答复
```

## 3. 需要完成的事项

### 3.1 启动并保护 MCP Server

- [ ] 选择并接入符合当前技术栈的 MCP Server SDK；对外提供稳定的 MCP Endpoint，推荐 Streamable HTTP。
- [ ] 配置服务地址、端口、路径、连接超时与请求超时；生产环境通过网关或服务发现访问，不暴露开发机地址。
- [ ] 为 MCP Endpoint 配置服务间认证（Token、mTLS 或现有内部鉴权机制）。
- [ ] 验证请求来源，并接收/校验经过签名的用户身份、租户、渠道和追踪上下文；不能信任调用方任意传入的 userId。
- [ ] 增加健康检查、就绪检查及工具清单检查，便于 `heyee-agent` 和监控系统判断服务可用性。

### 3.2 定义并注册业务工具

每个业务能力作为一个独立工具注册到本项目的 MCP Server。工具名是跨项目契约，发布后不可随意改名。

建议首批工具按明确业务边界拆分，例如：

| 工具 ID | 用途 | 示例关键参数 |
| --- | --- | --- |
| `order_query` | 查询订单状态、订单商品、售后关联信息 | `orderNo`、`queryType` |
| `logistics_query` | 查询物流节点和最新状态 | `orderNo` 或 `trackingNo` |
| `refund_query` | 查询退款/退货申请及处理进度 | `orderNo`、`afterSaleNo` |
| `coupon_balance_query` | 查询用户可用优惠券或余额汇总 | 用户身份、`status` |

- [ ] 为每个工具提供稳定的 `name`、面向模型和开发者都清晰的 `description`。
- [ ] 使用 JSON Schema 定义输入参数：类型、描述、枚举、默认值、必填字段和格式约束。
- [ ] Schema 中只保留业务查询真正需要的参数；用户、租户、权限上下文应从鉴权上下文获得，而非让模型自由填写。
- [ ] 在服务启动时完成工具注册，并确保 MCP `tools/list` 能返回完整定义。
- [ ] 工具名加业务前缀或保持全局唯一，避免未来多服务接入后的重名，例如 `commerce_order_query`。

### 3.2.1 将参数 Schema 作为唯一权威契约

`heyee-agent` 会基于 MCP `tools/list` 返回的 Schema 从自然语言中提取参数，但 **Schema 的定义权和最终解释权始终在本项目**。工具处理器不能假定调用方一定正确地提取了参数，也不能只依靠 Agent 侧补默认值。

- [ ] 每个参数准确声明 `type`、`description`、是否 `required`、`enum`、`default`、格式与上下限；描述应说明业务语义、单位和时间口径，而不只是字段名。
- [ ] 对枚举声明规范值，并在描述中列举重要的口语同义表达。例如 `queryType=ranking` 应说明其含义为“排名/排行/前几名”。
- [ ] 对日期/时间参数明确格式、时区和相对时间的解释边界；例如是接收 `2026-07-13`、月份标识还是由本服务解析自然语言，避免两边各自转换一次。
- [ ] 只为“未提供时仍安全且业务合理”的字段设置 `default`。默认值不能扩大数据范围、绕过权限或改变用户明确表达的条件。
- [ ] 必填但缺失的参数必须返回机器可识别的 `INVALID_ARGUMENT` / `MISSING_REQUIRED_PARAMETER` 类错误，并指出可展示给用户的缺失字段；不要用全量查询代替。
- [ ] Server 在执行前按同一 Schema 做类型、枚举、范围、字段白名单和跨字段组合校验；忽略或拒绝未声明字段。
- [ ] Server 对默认值再次兜底：即使 Client 未补齐默认值，也以本项目发布的默认语义执行；不得接受 Client 声称的、Schema 未声明的默认值。

示例：`limit` 是整数且默认值为 `10` 时，Server 应拒绝 `10.5`、负数、超限值和未声明字段；`10` 可以以 JSON 数字形式传入，但不得因为 Agent/SDK 的数值序列化差异而误判为非法。

### 3.3 实现工具处理器

- [ ] 每个工具处理器调用本项目已有的**应用服务接口**，而不是直接书写 SQL、操作 Redis Key 或复刻业务规则。
- [ ] 在进入应用服务前将已校验的参数转换为本项目的明确 DTO/查询对象；不要将不受约束的 `Map` 直接传到 SQL 拼接、缓存访问或下游请求。
- [ ] 复用既有的订单可见性、租户隔离、数据脱敏、售后状态解释和缓存策略。
- [ ] 对输入做严格校验：格式不合法、参数组合冲突、缺少查询标识时返回可识别的参数错误。
- [ ] 没有数据时返回“未查询到”的正常业务结果；无权限、参数错误、限流、下游异常应有不同错误语义。
- [ ] 返回小而确定的结构化数据，不返回整行数据库对象、内部错误堆栈、缓存内容或不必要的个人隐私字段。
- [ ] 大列表必须限制条数并支持分页/摘要；单次响应应有大小上限，避免大量数据进入模型上下文。

建议的业务结果形态：

```json
{
  "found": true,
  "orderNo": "2024112801",
  "status": "REFUND_PROCESSING",
  "statusText": "退款处理中",
  "latestLogistics": {
    "time": "2026-07-13T10:20:00+08:00",
    "description": "退货商品已签收"
  },
  "safeSummary": "退款处理中，预计 1-2 个工作日完成退款"
}
```

`safeSummary` 可帮助调用方直接理解结果，但它不是绕开结构化字段的唯一返回方式。

### 3.4 可靠性、性能与可观测性

- [ ] 为每个工具设置明确超时，并将超时控制在 Agent 总响应预算内；不要无限等待下游服务。
- [ ] 对高频查询设置限流、并发保护和连接池上限，防止对订单库和 Redis 造成放大流量。
- [ ] 只对安全的幂等查询按既有规范做有限重试；避免对已失败的下游进行无界重试。
- [ ] 将异常转换为 MCP 可识别的错误结果，不向调用方泄露堆栈、SQL、Redis Key、内部地址或敏感数据。
- [ ] 记录 traceId、工具名、结果分类、耗时、数据源类型和脱敏后的参数摘要；禁止记录原始身份证号、手机号、完整地址等敏感信息。
- [ ] 输出工具维度的成功率、P95/P99 耗时、超时率、限流次数、空结果率和下游错误率指标。
- [ ] 对依赖故障设计清晰降级：例如返回“实时订单服务暂不可用”，而不是返回旧缓存并伪装成实时结果。

### 3.5 版本与发布管理

- [ ] 工具名、参数字段和字段语义形成版本化契约；新增可选字段通常兼容，删除/改名/改变语义需要新版本工具。
- [ ] 在测试环境和生产环境分别提供 MCP Server 地址与独立凭证。
- [ ] 每次发布前执行 `initialize`、`tools/list` 和关键 `tools/call` 冒烟验证。
- [ ] 提供工具目录、参数示例、返回示例、错误码说明和变更记录给 `heyee-agent` 团队。
- [ ] Schema 变更（尤其是默认值、枚举、必填项、时间格式）纳入兼容性评审；这些字段会直接影响 Agent 的参数提取行为。

## 4. 交付给 heyee-agent 的信息

上线或联调前，需要提供：

- MCP Server 的环境地址、传输方式、认证方式、超时建议和网络访问要求；
- 每个工具的 ID、描述、完整 JSON Schema、必填字段和默认值；
- 业务结果样例、错误分类和敏感字段说明；
- 用户身份/租户上下文的传递规范；
- 限流配额、可用性目标、维护窗口和负责人；
- 测试账号/测试数据及可重复的联调用例。

## 5. 验收标准

- [ ] 未授权请求不能调用工具，且不能通过自填 userId 越权查询。
- [ ] `tools/list` 返回的工具名、描述和 Schema 与约定完全一致。
- [ ] 以缺失必填参数、无效枚举、错误数值类型、超范围值、未知字段和默认值缺失等用例验证服务端校验；所有校验均不能被 Client 绕过。
- [ ] 每个工具均复用既有业务服务，未引入对方项目直连 DB/Redis 的方案。
- [ ] 正常、无数据、参数错误、无权限、超时和下游失败均可区分并有脱敏返回。
- [ ] 关键工具具备审计日志、指标和告警，且单工具故障不会影响本项目核心业务服务。
- [ ] 与 `heyee-agent` 的端到端用例能够得到正确、可解释且不泄露敏感数据的回答上下文。
